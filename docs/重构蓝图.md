# EternisStarrySky 重构蓝图

这份文档用于约束后续重写方向。它不是简单的目录整理计划，而是用来明确：哪些代码该留在主 Mod，哪些该交给 Genesis Lib，哪些属于实验残留，哪些需要按功能域彻底重写。

## 基本原则

- `ISS/` 只作为 Iron's Spells 'n Spellbooks 的参考源码，不纳入本项目重构目标。
- `genesis_core` 是独立外部机制，本次不处理、不迁移、不清理。
- EternisStarrySky 只保留具体玩法内容。
- 可复用的底层能力放到 Genesis Lib。
- 客户端代码必须和通用/服务端代码分离。
- 每个领域尽量只使用一种注册风格。
- 每个阶段完成后都要保证项目仍然能编译、能启动。
- `src/main/resources` 下已有的自定义模型 JSON 默认视为手写资源，不确认废弃前不要删除或重新生成。

## 目标包结构

```text
miku.united_as_one.genesis
  Genesis.java
  common/
    registry/
    network/
    config/
    datagen/
    compat/
  content/
    block/
    item/
    equipment/
    curio/
    effect/
    spell/
    entity/
    world/
    workbench/
  gameplay/
    combat/
    spell/
    equipment/
    curio/
    save/
  client/
    event/
    model/
    particle/
    render/
    screen/
  integration/
    irons_spellbooks/
    jei/
    curios/
  mixin/
```

各包职责：

- `common.registry`：只放注册声明和注册入口。
- `content`：具体 Mod 内容，例如物品、方块、实体、法术、效果、菜单、配方。
- `gameplay`：运行时玩法系统和事件处理。
- `client`：任何可能引用 Minecraft 客户端类的代码。
- `integration`：与其他 Mod 的兼容和桥接。
- `mixin`：按目标和功能归类的 mixin。

## 留在主项目的内容

这些是 EternisStarrySky 的具体玩法内容，应该留在主项目里，但需要重写或整理：

- `contents.spell`：Genesis 自己的法术。
- `contents.items`：物品、武器、法术书、法杖、饰品、材料。
- `contents.block`：方块和工作台相关方块。
- `contents.effect`：MobEffect。
- `contents.entity`：怪物、投射物、法术实体。
- `contents.workbench`：奥术工作台、奥术坩埚。
- `registries.*`：注册类，后续需要按领域拆分。
- `handlers.*`：事件类，后续需要按功能和端分离。
- `compat.jei`：JEI 兼容。
- `data.datagen`：数据生成器。
- `data.save`：主 Mod 自己的存档数据。
- `resourcepacks/genesis_old`：旧资源包，除非明确废弃，否则作为可选资源包保留。

## 交给 Genesis Lib 的内容

这些能力偏底层、可复用，应该由 Genesis Lib 提供稳定 API：

- shader 注册和渲染辅助。
- cosmic item/render 辅助。
- tooltip 粒子和背景渲染 API。
- trail/slash effect API。
- 通用粒子渲染类型。
- damage policy / damage service。
- equipment stat 配置和管理器。
- Curios 槽位常量和通用工具。
- 通用 NBT / persistent data 工具。
- 数学、文本、颜色工具。
- 支撑 Genesis Lib 公共 API 的内部 mixin accessor。

主项目最终应该只依赖 `miku.bai_ze_li.genesis.api.*` 里稳定的 API，不再保留重复实现。

## 删除或隔离的内容

这些不应该进入正式生产注册：

- `contents.entity.test`
- `client.renderer.entity.test`
- 调试粒子和粒子调试事件，但要先确认对应实现已经迁入 Genesis Lib/API。
- `test`、`testa`、`testb` 等测试粒子 registry ID。
- 空置或废弃的网络 channel。
- `notuse` 包。
- `<null>`、`nop` 这类占位资源路径。
- `System.out.println`、大量 `printStackTrace` 调试输出。
- 已失效的大段注释代码。

如果某些调试工具仍然有价值，后续应放进 dev-only 开关或单独 debug source set。

注意：BloodBoss AI 里当前命名为 test 的 memory/activity 是实际玩法需要，不能删除。后续 AI 重写时应改成生产语义命名，而不是当测试残留清理。

## 重写设计方案

### 注册层

当前问题：

- 大型注册类混合了分类、构造、datagen、模型规则、tooltip 文本、外部 Mod 兼容。
- 静态字段顺序隐含依赖关系。
- 测试条目和正式条目混在一起。

目标设计：

- 保留一个小入口：`common.registry.GenesisRegistries`。
- 按内容类型拆分：
  - `GenesisMaterials`
  - `GenesisTools`
  - `GenesisWeapons`
  - `GenesisArmor`
  - `GenesisCurios`
  - `GenesisSpellItems`
  - `GenesisBlocks`
  - `GenesisWorkbenchBlocks`
  - `GenesisEntities`
  - `GenesisEffects`
  - `GenesisSpells`
  - `GenesisParticles`
- 只有在能明显减少重复时才引入小型 factory。
- datagen helper 可以靠近对应注册类，但不能把无关 provider 逻辑塞进大注册类。

### 物品与装备

当前问题：

- 一个装备的行为散在 item class、event class、mixin、tooltip、shader、stats 多个地方。
- 玩家问“这个装备做了什么”时，很难从一个包里看全。

目标设计：

- 每个重要装备系列独立成一个功能包：
  - `content.equipment.violet`
  - `content.equipment.divine_metal`
  - `content.equipment.celestial_source`
  - `content.equipment.chaos`
  - `content.equipment.gungnir`
- 每个系列内部保持固定结构：
  - 物品类。
  - 行为/事件类。
  - 客户端表现类。
  - 注册入口。
- 通用 stats 读写放 Genesis Lib。
- 平衡数值和具体玩法效果留在主项目。

核心规则：

- 一个装备的核心逻辑应尽量在同一个功能包内看完。

### 法术与效果

当前问题：

- 法术、MobEffect、事件、投射物、mixin 分布很散。
- 符文交互中存在大量重复的 Curios 检查。
- 一些法术行为依赖 mixin，但没有明确功能归属。

目标设计：

- 按法术学派组织：
  - `content.spell.chaos`
  - `content.spell.celestial_source`
  - `content.spell.fire`
  - `content.spell.ice`
  - `content.spell.thunder`
  - `content.spell.eldritch`
- 建立 `gameplay.spell` 作为跨学派规则层：
  - 法术穿透。
  - 符文修正。
  - 学派通用 hook。
- 用明确服务替代重复判断：
  - `RuneEffectRules`
  - `SpellSchoolRules`
  - `SpellDamageRules`
- 只有 Iron's Spells 没有事件或扩展点时才保留 mixin。

### 事件系统

当前问题：

- `EventHandler`、`ESSLivingEvent` 这类名字无法表达功能归属。
- 客户端 tooltip/render 逻辑混在通用事件类里。
- 大量散落的 subscriber 让行为来源难以追踪。

目标设计：

- 用功能命名事件类：
  - `gameplay.save.SaveEvents`
  - `gameplay.equipment.EquipmentStatEvents`
  - `gameplay.curio.RuneEvents`
  - `gameplay.spell.SpellCombatEvents`
  - `gameplay.effect.EffectSyncEvents`
  - `client.event.TooltipRenderEvents`
  - `client.event.ClientLivingRenderEvents`
- 每个事件类必须能直接看出：
  - 使用哪个 bus。
  - 运行在哪一端。
  - 属于哪个功能。
- 不因为事件类型相同就把无关逻辑塞进同一个类。

### 网络层

当前问题：

- packet channel 和 packet 包结构不统一。
- 有空置 channel。
- packet 按实现偶然性分组，而不是按功能分组。

目标设计：

- 默认只保留一个 channel。
- packet 按功能分包：
  - `sync`
  - `spell`
  - `workbench`
  - `client_effect`
- packet 名称写清方向和目的：
  - `SyncDeadEntitiesS2CPacket`
  - `SyncWireBoxS2CPacket`
  - `TransferArcaneWorkbenchRecipeC2SPacket`
  - `SpawnSlashEffectS2CPacket`
- 所有 packet 注册集中到 `GenesisNetwork`。

### 客户端渲染

当前问题：

- `client.render`、`client.renderer`、`contents.entity.*Renderer` 同时存在。
- 一部分渲染 API 已迁到 Genesis Lib，但主项目仍有旧包装。
- 调试渲染和正式渲染混在一起。

目标设计：

- `client.render` 放渲染系统和辅助。
- 实体渲染统一放到 `client.render.entity`。
- 物品、方块、screen 渲染各自放明确目录。
- shader、cosmic、tooltip、trail 等通用能力从 Genesis Lib 引用。
- 主项目只保留具体视觉配置和 Mod 专属 renderer。

### 工作台系统

当前问题：

- 奥术工作台和奥术坩埚的 block、menu、recipe、JEI、screen、packet 分散在多个包里。

目标设计：

- 每个工作台作为完整功能模块：
  - `content.workbench.arcane`
  - `content.workbench.arcane_cauldron`
- 每个模块自己拥有：
  - block。
  - block entity。
  - menu。
  - screen。
  - recipe。
  - serializer/type 注册。
  - JEI category / transfer。
  - 必要 packet。
- 通用工作台工具放 `content.workbench.common`。

### Mixin

当前问题：

- mixin 主要按目标路径组织，而不是按“为什么存在”组织。
- 修改 mixin 时很难知道会影响哪个玩法功能。

目标设计：

- 保留目标路径组织也可以，但必须记录功能归属。
- 在大规模修改前先做 mixin 清单：
  - target class。
  - 注入方法。
  - 功能归属。
  - 为什么不用事件/API。
  - 什么时候可以删除。
- 优先保留少量解释清楚的 mixin，而不是大量无说明的小注入。

## 重写顺序

### Phase 1：边界清理

- 完成主项目旧 API 到 Genesis Lib API 的替换。
- 删除主项目里已经被 Genesis Lib 替代的重复 API 实现。
- 把客户端事件从通用事件类中拆出去。
- `genesis_core` 不处理，保持独立外部机制。

完成标准：

- dedicated server 不会因为加载通用类而触碰客户端包。
- 主项目不再保留 Genesis Lib 已提供能力的重复实现。

### Phase 2：注册层重写

- 拆分 `ItemRegistry`：
  - materials
  - tools
  - weapons
  - armor
  - curios
  - spellbooks/staffs/manuscripts
  - misc/special items
- 拆分 `BlockRegistry`：
  - stone/wood block sets
  - plants/crops
  - ores/material blocks
  - workbench blocks
  - portal/dimension blocks
- `ModRegistries` 只保留注册入口职责。
- 清理 `CreativeTabRegistry` 中隐含的额外注册副作用。

完成标准：

- 每个注册文件能在一轮阅读中理解。
- datagen helper 不再埋在巨大注册类深处。

### Phase 3：事件系统重写

- 用 feature event 替代散落 subscriber。
- tooltip 和客户端渲染事件迁入 `client.event`。
- server lifecycle 和 save sync 归入 `gameplay.save`。
- 取消泛用 `EventHandler` 这类名字。

完成标准：

- 行为能从功能包追踪到事件。
- common 事件类没有客户端引用。

### Phase 4：网络层重写

- 合并空置或重复 channel。
- packet 按功能和方向命名。
- 集中注册 packet。

完成标准：

- 没有空 channel。
- Join sync、workbench transfer、slash effect、GoodCake packet 都能从名字看出方向和目的。

### Phase 5：Mixin 清点

- 按功能清点所有 mixin。
- 判断哪些 mixin 已经能被 Genesis Lib 或事件替代。
- 给保留的 mixin 写明原因。

完成标准：

- `mixins.genesis_magic.json` 可以按功能解释。
- 每个 mixin 都有明确保留理由。

### Phase 6：资源与 Datagen

- `src/main/resources` 只放手写资源。
- `src/generated/resources` 保持可重新生成。
- 给旧资源包做一个简短清单。
- 删除测试配方和无引用占位资源。
- 默认保留 `src/main/resources` 下的自定义模型 JSON。

完成标准：

- datagen 可以重新生成生成资源。
- 旧资源是有意保留，不是误复制。

## 近期执行队列

1. 审计当前 Genesis Lib 迁移后的 import，删除主项目死 API。
2. 从 `handlers.EventHandler` 拆出客户端 tooltip/render 逻辑。
3. 删除或隔离 test entity / test particle 注册。
4. 合并 `NetworkHandler` 和 `ModPacketHandler`。
5. 先拆 `ItemRegistry` 的 materials 和 weapons。
6. 再拆 `BlockRegistry` 的 block set 和 special block。
7. 注册层稳定后，再开始按功能重写事件系统。

## 验证清单

每个阶段后至少执行：

- `gradlew compileJava`
- `gradlew processResources`
- 客户端能启动。
- dedicated server 能启动。
- 如果改了数据或资源，datagen 能跑完。

手动检查：

- 物品和方块出现在正确创造标签页。
- Iron's Spells 能加载新增法术。
- Curios 和符文效果仍然触发。
- tooltip / shader 效果只在客户端渲染。
- 玩家进服同步 packet 不报错。
